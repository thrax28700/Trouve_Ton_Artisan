1. Contexte du projet

1.1 Présentation de l'entreprise

La Région Auvergne-Rhône-Alpes est une collectivité territoriale couvrant 12 départements dans le quart sud-est de la France. Elle dispose de bureaux à Lyon et à Clermont-Ferrand. Le projet est mené en relation avec l'antenne de Lyon, située au :

101 cours Charlemagne — CS 20033
69269 LYON CEDEX 02 — France
+33 (0)4 26 73 40 00
www.auvergnerhonealpes.fr

L'artisanat occupe une place majeure dans l'économie régionale : près d'un tiers des entreprises de la région sont des entreprises artisanales, soit 221 000 entreprises recensées en 2021. La région Auvergne-Rhône-Alpes est ainsi l'une des régions les plus artisanales de France, et souhaite entretenir cet engouement par la création d'une plateforme numérique dédiée.

1.2 Expression des besoins

La Région Auvergne-Rhône-Alpes mandate la création d'une plateforme web dédiée aux artisans de la région, permettant aux particuliers de les trouver facilement et de leur adresser des demandes de renseignements, prestations ou tarifs via un formulaire de contact.

4. Sécurité

4.1 Architecture de sécurité

L'application repose sur une séparation stricte entre le frontend et le backend :

  • Le frontend React est une application statique : il ne contient aucun secret, aucune logique métier sensible, aucun accès direct à la base de données.
  • Le backend Node.js/Express est la seule couche qui interroge MySQL. Toutes les opérations de données passent exclusivement par son API REST.
  • La base de données MySQL n'est jamais exposée publiquement.

4.2 Mesures de sécurité mises en place

Clé API — Authentification des requêtes publiques

Chaque requête vers l'API doit inclure l'en-tête X-API-Key. Un middleware custom vérifie sa validité via une comparaison timing-safe (crypto.timingSafeEqual) pour éviter les attaques temporelles.

AspectDétail
Mise en œuvrebackend/middleware/apiKey.js
IntérêtEmpêche tout accès à l'API depuis une source non autorisée
En cas d'échecRetourne 401 Unauthorized

JWT — Authentification de l'espace administration

L'accès aux routes /api/admin/* est protégé par un token JWT signé avec une clé secrète.

AspectDétail
Mise en œuvrebackend/middleware/auth.js + jsonwebtoken
IntérêtSessions sécurisées sans état côté serveur (stateless)
Durée de vie8 heures — renouvellement requis après expiration

En-têtes HTTP sécurisés — Helmet

En-tête HTTPRôle
Content-Security-PolicyRestreint les sources de scripts, styles et médias autorisés
X-Frame-Options: DENYProtège contre le clickjacking (intégration en iframe)
X-Content-Type-Options: nosniffEmpêche le navigateur de deviner le type MIME
Strict-Transport-SecurityForce HTTPS en production
Referrer-PolicyContrôle les informations envoyées au serveur référent

Limitation de débit — Rate Limiting

PortéeLimiteIntérêt
API globale (dev)2 000 requêtes / 15 minDéveloppement sans blocage
API globale (prod)100 requêtes / 15 minProtection contre le scraping et les attaques par force brute
Formulaire contact5 messages / heurePrévention du spam

Protection XSS — xss-clean

Toutes les données entrantes (body, query, params) sont nettoyées automatiquement pour supprimer les balises HTML et scripts malveillants avant tout traitement.

AspectDétail
Mise en œuvreMiddleware xss-clean appliqué globalement
IntérêtNeutralise les attaques XSS (Cross-Site Scripting) avant qu'elles atteignent la logique applicative

Protection HPP — HTTP Parameter Pollution

Le middleware hpp empêche les attaques par duplication de paramètres dans les query strings (ex : ?categorie=foo&categorie=bar).

CORS — Cross-Origin Resource Sharing

L'API n'accepte les requêtes que depuis les origines explicitement autorisées. Toute requête d'une origine non listée est refusée par le navigateur avant même d'atteindre le serveur.

Protection contre les injections SQL — Sequelize ORM

L'ORM Sequelize utilise des requêtes paramétrées (prepared statements) pour toutes les interactions avec MySQL. Aucune interpolation directe de chaîne SQL n'est présente dans le code, ce qui rend les injections SQL impossibles.

Validation des entrées — express-validator

Tous les champs du formulaire de contact sont validés côté serveur avant traitement :

ChampValidation appliquée
nomNon vide, entre 2 et 100 caractères, caractères spéciaux échappés
emailFormat email valide, normalisé
objetNon vide, entre 2 et 200 caractères, échappé
messageNon vide, entre 10 et 1 000 caractères, échappé
artisan_idEntier positif valide

Masquage des données sensibles

Le champ email des artisans est exclu de toutes les réponses API via Sequelize (attributes: { exclude: ['email'] }). L'email n'est utilisé qu'en interne côté serveur pour l'envoi du formulaire de contact.

Hachage des mots de passe — bcryptjs

Le mot de passe de l'administrateur est haché avec bcryptjs (coût 10) avant stockage. Le mot de passe en clair n'est jamais persisté en base de données.

4.3 Variables d'environnement

Tous les secrets sont stockés dans un fichier .env non versionné (présent dans .gitignore). Un fichier .env.example sans valeurs sensibles est fourni dans le dépôt.

VariableRôle
DB_HOST / DB_USER / DB_PASSWORDConnexion à la base de données MySQL

JWT_SECRETClé de signature des tokens administrateur

5.2 Vulnérabilités OWASP Top 10 — Analyse et réponse

#Vulnérabilité OWASPRisqueMesure appliquée dans ce projet
A01 Broken Access Control Critique Routes admin protégées par JWT. Clé API sur routes publiques. Middleware de vérification systématique.
A02 Cryptographic Failures Critique Mots de passe hachés via bcryptjs (coût 10). Secrets dans .env non versionné. HTTPS en production.
A03 Injection (SQL, NoSQL, OS) Critique ORM Sequelize avec requêtes paramétrées. Aucune concaténation de chaîne SQL dans le code.
A04 Insecure Design Important Architecture frontend/backend séparée. Données sensibles (emails artisans) non exposées via l'API publique.
A05 Security Misconfiguration Important Helmet configure automatiquement les en-têtes HTTP. CORS restrictif. NODE_ENV différencié dev/prod.
A06 Vulnerable Components Important npm audit exécuté régulièrement. Dépendances maintenues à jour. Versions verrouillées dans package-lock.json.
A07 Authentication Failures Critique Rate limiting (5 tentatives/heure sur le contact). JWT à durée limitée. Comparaison timing-safe pour la clé API.
A08 Data Integrity Failures Important Validation complète côté serveur avec express-validator (typage, longueur, format). Double validation frontend + backend.
A09 Logging & Monitoring Failures Important Morgan pour le logging des requêtes HTTP. Gestionnaire d'erreurs global. Logs différenciés dev/prod.
A10 Server-Side Request Forgery Faible Aucune requête serveur vers des URL externes non contrôlées. Le backend n'effectue pas de fetch vers des ressources distantes inconnues.

5.3 Failles identifiées et corrigées durant le projet

Faille 1 — Email artisan exposé dans l'API publique

AspectDétail
DescriptionLes adresses e-mail des artisans étaient retournées dans les réponses JSON de l'API publique (liste et fiche artisan).
RisqueCollecte automatisée d'adresses e-mail (harvesting) pouvant mener à du spam ou du phishing ciblé.
CorrectionExclusion du champ email via Sequelize : attributes: { exclude: ['email'] } sur toutes les routes publiques. L'email est utilisé uniquement côté serveur pour l'envoi du formulaire de contact.

Faille 2 — Absence de validation côté serveur du formulaire de contact

AspectDétail
DescriptionLe formulaire de contact n'effectuait aucune validation des données côté serveur. Un attaquant pouvait soumettre des données malformées, des scripts ou des chaînes très longues.
RisqueInjections XSS via le message, pollution de la base de données, envoi de spam massif via l'API.
CorrectionImplémentation d'express-validator avec trim, escape, longueur maximale, et format email. Rate limiting spécifique (5 messages/heure) pour prévenir le spam.

Faille 3 — Secrets versionnés dans le dépôt Git

AspectDétail
DescriptionLes fichiers .env contenant les mots de passe, clés JWT et clés API risquaient d'être inclus dans le dépôt Git.
RisqueExposition publique de tous les secrets de l'application si le dépôt est public (GitHub).
CorrectionAjout de .env et **/.env dans .gitignore. Fourniture d'un .env.example avec des valeurs fictives pour guider l'installation.

Faille 4 — CORS ouvert à toutes les origines

AspectDétail
DescriptionSans configuration CORS, Express accepte les requêtes depuis n'importe quelle origine, permettant à n'importe quel site d'interroger l'API.
RisqueAttaques Cross-Origin : un site malveillant peut exploiter la session d'un utilisateur authentifié pour envoyer des requêtes à l'API.
CorrectionConfiguration CORS stricte avec une liste blanche d'origines autorisées (localhost:5173 en dev, domaine de production en prod). Toute autre origine est refusée.

Faille 5 — Dépendances tierces vulnérables (audit du 26/07/2026)

AspectDétail
Descriptionnpm audit a révélé 8 vulnérabilités dans les dépendances backend : DoS sur body-parser, brace-expansion, qs ; falsification de logs sur morgan ; et 7 CVE critiques sur nodemailer (injection SMTP, injection CRLF, contournement de la protection anti-SSRF).
RisqueDéni de service applicatif, logs corrompus, et — pour nodemailer — envoi de mails vers des domaines détournés ou exécution de commandes SMTP arbitraires via le formulaire de contact.
Correctionnpm audit fix pour les 4 premières (mise à jour non-cassante). Mise à jour manuelle de nodemailer (6.10.1 → 9.0.3), testée sans régression sur l'envoi de messages. La dépendance sqlite3, inutilisée et incohérente avec l'imposition de MySQL par le cahier des charges, a été supprimée.
Vulnérabilité résiduelle assuméeUne faille modérée sur uuid (dépendance transitive de Sequelize) n'a pas été corrigée : la résolution automatique proposait de rétrograder Sequelize en version 3 (obsolète), ce qui aurait cassé l'ensemble de l'ORM. La faille ne s'exploite que si un buffer est fourni explicitement à une fonction uuid, ce que le code ne fait jamais — risque jugé nul, à réévaluer à la prochaine mise à jour majeure de Sequelize.

Résultats détaillés de la validation W3C

Le HTML final (après rendu React) a été validé page par page via l'API du Nu Html Checker :

PageRésultat

Liste des artisans (/artisans)0 erreur
Fiche artisan (/artisans/:id)0 erreur

Deux erreurs réelles ont été détectées puis corrigées durant cette validation :

  • <main> imbriqué — les pages Liste des artisans et 404 plaçaient un second <main> à l'intérieur du <main> global du layout (interdit par la spec HTML5, un seul <main> visible par document). Remplacé par <div role="region">.
  • aria-label invalide sur <span> — le badge « En vedette » portait un aria-label redondant avec son texte visible, interdit sur un élément de rôle générique. Attribut supprimé (le texte visible suffit pour l'accessibilité).
  • Saut de niveau de titre — sur la page 404, le <h1> était suivi directement d'un <h3> dans le pied de page (aucun <h2> intermédiaire). Les titres de colonnes du footer sont passés de <h3> à <h2>.

La validation CSS du bundle compilé (frontend/dist/assets/*.css) ne remonte aucune erreur ; les 262 avertissements sont uniquement des préfixes vendeurs (-webkit-, -moz-, -o-) injectés automatiquement par l'autoprefixer de Bootstrap/Vite et des avertissements attendus sur les variables CSS (--*), non évaluables statiquement par le validateur — aucun n'indique une erreur de code.
